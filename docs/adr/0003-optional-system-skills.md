# System skills can be mandatory or optional, chosen per SKILL.md

ADR 0002 made every system (builtin) skill mandatory: auto-attached to every `AgentDefinition`, with no way to detach it. In practice not every system-authored skill belongs on every agent — some are narrow enough (a specific review checklist, a niche integration) that they should ship curated and read-only, but still be something the user opts an agent into, the same way a custom skill is chosen.

We're splitting system skills into two subtypes, declared per skill rather than per deployment:

- **Mandatory** (the ADR 0002 default): auto-attached to every `AgentDefinition`, cannot be detached.
- **Optional**: not attached anywhere by default; the user picks it per `AgentDefinition` from a checklist, exactly like a custom skill. Content is still read-only — the user can attach/detach it, not edit it.

Key decisions:

- **The subtype is a new `mandatory` frontmatter field in `SKILL.md`**, parsed alongside the existing `name`/`description` fields (`parse_skill_md`, `repo/skill.rs`). Accepted values are the literal strings `true`/`false` (case-insensitive). **The field is optional and defaults to `true`** when absent — every skill written before this ADR (and any skill author who doesn't think about the distinction) keeps today's mandatory behavior with zero migration and zero risk of an existing skill silently becoming droppable.
- **Per-agent optional-skill selection is a new `agent_definition.selected_builtin_skill_ids` column** (migration `0006`), a JSON array of skill ids — mirroring the existing `session.launched_skill_ids` column's "ordered id array as JSON text" convention, not a new table. This is a deliberate departure from how custom-skill attachment works (`agent_skill`, a join table): `agent_skill.skill_id` carries `REFERENCES skill(id) ON DELETE CASCADE`, and the app runs with `PRAGMA foreign_keys = ON` (`db.rs`'s `foreign_keys(true)`, verified by its own `foreign_keys_enforced` test) — inserting a builtin id, which is never a row in the `skill` table (ADR 0002), would violate that constraint outright. Rebuilding `agent_skill` to loosen or drop the FK is possible but is schema surgery for no real benefit over the JSON-column pattern this codebase already uses for exactly this shape of data.
- **One shared function computes the effective mandatory+optional builtin set: `repo::skill::effective_builtin_skills(selected_optional_ids)`.** Both `content_for_agent` (what actually gets injected at launch) and `commands::agent::list`'s `skillIds` annotation (what the Roster compares against the launch snapshot to show "Restart to apply") call this one function. ADR 0001's shipped v1 had a Critical bug caught only at final review because two call sites computed "the agent's builtin skill ids" via separate logic that quietly drifted; this ADR closes that class of bug by construction instead of by review discipline.
- **The frontend reuses the existing `skillIds` attach/detach wiring end to end — no new IPC fields.** `Builder.tsx`'s "Skills" section already sends whatever the user checked as `skillIds` on save; today only custom skills have checkboxes (system skills are static badges). This ADR adds a second checkbox group for optional system skills, feeding the exact same `skillIds` array and the exact same save request field. `commands::agent::save` now splits an incoming `skillIds` entry three ways: a real custom DB skill id → `agent_skill` (unchanged), an optional builtin's id → `agent_definition.selected_builtin_skill_ids`, anything else (a mandatory builtin id, an unknown id) → silently dropped, mirroring the existing "filter to known ids" precedent for custom skill ids. On load, `AgentDefinition.skillIds` already reflects the full effective set (mandatory + currently-selected-optional + custom, via `effective_builtin_skills`), so the optional-skill checkboxes come back pre-checked with no additional frontend state.
- **`SkillLibrary.tsx`'s System section gets a visual "Always on" / "Optional" indicator but no new interaction** — attaching/detaching an optional system skill happens in `Builder.tsx` (per-agent), the same place custom-skill attachment already happens; the Library stays the CRUD/browse surface, not the attach surface, matching the existing split of responsibility between the two components.
