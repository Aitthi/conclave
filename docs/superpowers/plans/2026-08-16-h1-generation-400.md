## Task

Find why the generation request 400s, fix it, pin it with a regression test.

## Where the request is built

`src-tauri/src/engine/runtime/ctx_proxy.rs` ~line 2027-2080 (SummaryJob step
4-5): `prefix = count_tokens::prefix_messages(&messages, earliest)` then
appends ONE `{"role":"user"}` instruction message, then
`gen_body = {model, max_tokens: 8192, tool_choice: {"type":"none"}, messages}`

`src-tauri/src/engine/runtime/summary.rs::generate_summary`.

## Hypotheses, most likely first — verify, do not assume

1. **Dangling tool_use at the prefix boundary.** If `prefix` ends with an
   assistant message whose last content blocks include `tool_use`, the next
   message must contain the matching `tool_result` blocks; our appended user
   instruction does not → classic 400. `prefix_messages` is the CACHE closure
   authority; nothing proves it guarantees TOOL closure.
2. **Mid-conversation `{"role":"system"}` message rules.** Claude Code on
   opus-5 emits system turns inside `messages`. API rule: such a message must
   follow a user message AND must be last or be followed by an assistant turn.
   A prefix slice ending on a system message followed by our user instruction
   → 400. (Also check: system message immediately after an assistant
   tool_use turn inside the prefix.)
3. **Beta-header mismatch.** The CLI runs `claude-opus-5[1m]` and sends beta
   headers; `generate_summary` forwards some set (see its tests around lines
   300-330). If a body shape in `messages` needs a beta the gen request drops
   (or vice versa) → 400.
4. Anything else the reconstructed body reveals (e.g. unknown top-level field
   copied from the original; opus-5 rejects `temperature`/`top_p`/`top_k` —
   the builder does not copy them today, but confirm nothing else leaks in).

## Outcome (2026-08-16, amended by owner after review)

- **Hypothesis 2 CONFIRMED** by live-API repro (Dew): `ct::prefix_messages`
  guarantees TOOL closure only; the closed prefix may stop ON a Claude Code
  mid-conversation `{"role":"system"}` message (beta
  `mid-conversation-system-2026-04-07`), and appending the H1 user
  instruction after it returns 400 `messages.N: role 'system' must precede
  an 'assistant' message or end the array`. Asymmetry that hid it:
  `count_tokens` ACCEPTS such a prefix, so A/B/C counted fine and only
  generation failed.
- **Hypotheses 1, 3, 4 REFUTED** with live probes: tool closure already
  holds; the beta-header sweep showed no difference; no sampling params leak
  into the gen body. Consecutive user roles are accepted by today's API.
- **Fix**: `ct::prefix_messages_before_appended_user` (walks back over both
  open tool exchanges AND a trailing system message) used for the generation
  body ONLY; `prefix_messages` / C / R = a − c unchanged. Lane
  `lane/h1-generation-400` @ 9dcc28f, 2 mutation-verified regression tests,
  mock upstream now enforces the API placement rule.
- **Observability ruling (owner)**: `runtime_prefix_messages` keeps recording
  the C prefix, which may exceed the generation prefix by ≥1. DEFERRED — no
  schema change for a diagnostic-only column; the integration test pins the
  cache≥gen invariant. Revisit only if a real diagnosis needs the gen-prefix
  length persisted.
