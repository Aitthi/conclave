## Decisions (Detoro, final — rejected alternatives recorded)
- D1. Tier set is `trivial` | `routine` | `standard` | `complex`, defined by SCOPE OF DECISION (the human's criterion): trivial = run a named command and report facts; routine = follow an existing pattern, decide nothing; standard = a whole feature inside ONE module, internal decisions allowed, no shared interface touched; complex = crosses modules, creates a pattern, or changes an interface / schema / concurrency / security, or the spec is still ambiguous. Tie-break: when two tiers fit, the higher wins; a Runner never receives a task that edits program logic.
- D2. New builtin role ids: `implementer-standard` ("Implementer (Standard)"), `reviewer-standard` ("Reviewer (Standard)"), `reviewer-complex` ("Reviewer (Complex)"). Existing ids are NOT renamed (`implementer-complex`, `reviewer`, …) — stored `agent_definition.role_id` rows reference them (Armin on `reviewer`, Dew on `implementer-complex`). knock2 → `implementer-standard` and Mellow → `reviewer-complex` are agent-definition edits the human (or Detoro via `agentDef.save`) makes after the rebuild; the generic `reviewer` role stays for Armin and any future generalist.
- D3. New builtin skill `reviewer` (compact, ≤ 70 lines) bundled by `reviewer`, `reviewer-standard`, `reviewer-complex` INSTEAD of `implementer` (183 lines of build instructions a reviewer must not follow; the human wants comment-only reviewers). Rejected: keeping `implementer` on reviewers for its "grilling discipline" — that discipline is two bullets and is restated in the reviewer skill.
- D4. New builtin skill `tiering` (`mandatory: false`) bundled by `lead` and `coordinator`: the rubric, who tiers when, the Standard rules, the review routing table. Rejected: folding it into `leadership` only (the Coordinator applies it at dispatch and does not carry `leadership`); making it mandatory (workers never tier).
- D5. The Coordinator derives a tier ONLY when a task-table row lacks one (or the task has no table), records `TIER <tier> derived <reason>` as a note before `DISPATCH`, and never overrides a tier the lead wrote. The Coordinator never re-tiers.
- D6. Review routing by tier, with FALLBACK so 3.1 / 3.3 are in force before the Standard reviewer exists: `trivial` → no reviewer (the Coordinator checks the gate ledger); `routine` / `standard` → an idle Reviewer (Standard), else Reviewer (Complex), else Reviewer; `complex`, any task whose role is `designer`, or any row the lead marks `review: complex` (shared interface, security) → Reviewer (Complex), else Reviewer. A Reviewer (Standard) that finds a shared interface, schema, or security surface in the diff posts `REVIEW-REROUTE <slug> @<sha> complex <reason>` and stops; the Coordinator re-dispatches to Reviewer (Complex). It is not a review round.
- D7. Runner gate re-run is a step of the Coordinator's review loop (in `coordinator/SKILL.md`, the agent that executes it), with the Runner-side mechanics in `runner/SKILL.md`. A gate re-run does NOT claim the task: `add_gate` (`src-tauri/src/engine/repo/task.rs:431`) has no claimant check and stamps the actor id, so the ledger shows who ran it. No idle Runner → `GATES-SKIPPED <slug> @<sha> no idle runner`, straight to review; the rule saves tokens and must never block the pipeline. Rejected: a `gates-<slug>` task per lane (table noise, a claim to release).
- D8. Implementer READY shape gains three lines after `note:` — `changed:` / `why:` / `unsure:` (one line each, `unsure: none` allowed). The reviewer starts from `unsure:`. The Coordinator forwards the READY note id to the reviewer; a READY without the three lines gets the standard one-line re-post reply.
- D9. Standard `needs_decision`: an Implementer (Standard) that must touch a shared interface posts `BLOCKED` with `status: needs_decision` naming the interface and the consumers; the Coordinator escalates (condition 1); the lead re-tiers the task to `complex` by plan amendment and the Coordinator re-dispatches. The implementer does not widen the task and does not pick a workaround.
- D10. Milestone-end spot-check: on `ESCALATION milestone-done` the Coordinator lists which merged slugs were Standard-reviewed; the lead dispatches a spot-check of at least one to Reviewer (Complex) (`task note SPOT-CHECK <slug> @<sha>` → verdict in the same shape). A category that slips twice is marked `review: complex` in future plans. Skills name ROLES, never agents.
